## 🤖 Claude

Yes, that's clear, and I agree. What you're describing is called building in **vertical slices**: you finish one feature through every layer (model, frontend, backend, tests) before starting the next one. The current plan builds in **horizontal layers** instead: all models first, then all screens, then all of the backend. Layers are the reason it felt too big. You have to design everything up front without seeing any of it work. With slices, every milestone ends with something you can click through, and each data model is designed when you actually need it.

## The order of steps for each feature

Your four steps are good. I'd add three things:

0. **Scope.** A short list of what the feature does and what it leaves out for now. For login, that could be "sign up, log in, log out. Email verification and password reset come later." This step keeps a slice small.

## Error page

**When it shows:** when a page crashes while rendering, for example because of a bug or unexpected data. React Router catches the error and shows the route's `errorElement` instead of the page. Right now there isn't one, so React Router shows its own developer screen.

**Where it's attached:** in two places, with the same `ErrorPage` component.
- **Around the pages**, inside `AppLayout`. If a page crashes, the AppBar stays and the error appears where the page was.
- **On the root route**, as a fallback for the rare case that `AppLayout` itself crashes. Then the error page is shown without the AppBar.

**Content**
- Title: "Something went wrong"
- Description: "An unexpected error happened. Please try again."
- Buttons: "Try again" (reloads the page) and "Back to home".
- **Error details only in development:** the error message and stack trace, in a small box, so you see the cause while coding. Users never see them.

**What it does not cover:** errors in click handlers and failed API calls. React Router doesn't catch those. They'll be shown as notifications (step D) or inside the component (for example, "Could not load your alerts").

**A shared component.** The 404 page and the error page have the same shape: an icon, a title, a text and buttons. Following our "used in 2 places" rule, I'd create `global/components/StatusMessage/` and build both pages from it. The 404 page then gets an icon too.

## Loading

One `Loading` component in `global/components/Loading/`, with two forms:
- **`<Loading fullPage />`:** a centered spinner that fills the content area. We'll use it while checking whether the user is logged in (milestone 1), and later while lazy-loaded pages are loading.
- **`<Loading />`:** a smaller inline spinner, for inside a card or a section.

Details:
- **Accessibility:** screen readers announce "Loading…" (`role="status"` with a translated label).
- **Short delay before it appears (~300 ms):** fast requests then don't flash a spinner for a split second. Optional, but a common pattern. Do you want it?
- **Loading inside buttons needs no component of our own:** MUI's `Button` has a built-in `loading` prop. It's the same situation as with the form fields.
- **Skeletons** (grey placeholder blocks shaped like the content) come later, for lists such as "My alerts". MUI has a `Skeleton` component for that.

## PageLayout component

It goes in `global/components/PageLayout/`. Every page uses it, so all pages share the same heading, spacing and browser tab title.

```
┌───────────────────────────────────────────────┐
│ My alerts                      [+ New alert]  │  ← title (h1) + optional actions
│ Get notified when news matches your rules.    │  ← optional description
│                                               │
│ (page content)                                │
└───────────────────────────────────────────────┘
```

- **Props:** `title`, an optional `description`, optional `actions` (buttons) and `children`.
- **Responsive:** on desktop, the actions sit to the right of the title. On mobile, they move below it and take the full width.
- **Browser tab title:** it sets the tab title to "My alerts · Alert App". React 19 can render a `<title>` from inside any component, so no extra library is needed. This also helps accessibility, because screen readers announce the page title on navigation.
