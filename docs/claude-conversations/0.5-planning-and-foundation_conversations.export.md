● Yes, that's clear, and I agree. What you're describing is called building in
  vertical slices: you finish one feature through every layer (model, frontend,
  backend, tests) before starting the next one. The current plan builds in
  horizontal layers instead: all models first, then all screens, then all of the
  backend. Layers are the reason it felt too big. You have to design everything
  up front without seeing any of it work. With slices, every milestone ends
  with something you can click through, and each data model is designed when you
  actually need it.

  The order of steps for each feature

  Your four steps are good. I'd add three things:

  0. Scope. A short list of what the feature does and what it leaves out for
     now. For login, that could be "sign up, log in, log out. Email verification
     and password reset come later." This step keeps a slice small.
  1. Model
  2. API contract (new). Before any frontend code, agree on the endpoints, the
     request/response shapes and the Zod schemas in packages/shared. This
     matters because the frontend comes before the backend in your order. The
     frontend needs to know what the backend will return. With a contract, both
     sides are built against the same agreement, and the frontend can use mocks
     until the backend is ready.
  3. Frontend: pages, hooks, forms, translations, plus loading, error and empty
     states
  4. Backend
  5. Tests
  6. Wrap-up (new). Run npm run format, update PROJECT_PLAN.md, you review, you
     commit.

● Form fields

  No, we don't need them in advance. MUI's TextField works with React Hook Form
  as it is. A wrapper only saves repetition: every field needs RHF's Controller
  (or register), the error and helperText props, and translating the Zod error
  message with t(). That's about 10 lines per field, written the same way every
  time.

  We'll notice that repetition when we build the login form, so that's the right
  time to write the wrappers. I'll move them out of Phase 0.5 and into
  milestone 1.

  These are the decisions I'd like you to make:

  1. features/ or type-based folders? I recommend features/, because it matches
     how we'll work now: one milestone is mostly one folder. The rule would be
     that code used by only one feature lives in that feature, and code used by
     two or more moves to components/ or utils/.
  2. Generic pages: should they stay in src/pages/, or should they move into
     features/core/ (or similar)? I'd keep src/pages/. It's simple, and it'll
     only ever hold a few files.
  3. Orval output: one src/api/generated/ folder, or a split per feature? Orval

  Error page

  When it shows: when a page crashes while rendering, for example because of a
  bug or unexpected data. React Router catches the error and shows the route's
  errorElement instead of the page. Right now there isn't one, so React Router
  shows its own developer screen.

  Where it's attached: in two places, with the same ErrorPage component.
  - Around the pages, inside AppLayout. If a page crashes, the AppBar stays and
    the error appears where the page was.
  - On the root route, as a fallback for the rare case that AppLayout itself
    crashes. Then the error page is shown without the AppBar.

  Content
  - Title: "Something went wrong"
  - Description: "An unexpected error happened. Please try again."
  - Buttons: "Try again" (reloads the page) and "Back to home".
  - Error details only in development: the error message and stack trace, in a
    small box, so you see the cause while coding. Users never see them.

  What it does not cover: errors in click handlers and failed API calls. React
  Router doesn't catch those. They'll be shown as notifications (step D) or
  inside the component (for example, "Could not load your alerts").

  A shared component. The 404 page and the error page have the same shape: an
  icon, a title, a text and buttons. Following our "used in 2 places" rule, I'd
  create global/components/StatusMessage/ and build both pages from it. The 404
  page then gets an icon too.

  Loading

  One Loading component in global/components/Loading/, with two forms:
  - <Loading fullPage />: a centered spinner that fills the content area. We'll
    use it while checking whether the user is logged in (milestone 1), and later
    while lazy-loaded pages are loading.
  - <Loading />: a smaller inline spinner, for inside a card or a section.

  Details:
  - Accessibility: screen readers announce "Loading…" (role="status" with a
    translated label).
  - Short delay before it appears (~300 ms): fast requests then don't flash a
    spinner for a split second. Optional, but a common pattern. Do you want it?
  - Loading inside buttons needs no component of our own: MUI's Button has a
    built-in loading prop. It's the same situation as with the form fields.
  - Skeletons (grey placeholder blocks shaped like the content) come later, for
    lists such as "My alerts". MUI has a Skeleton component for that.
